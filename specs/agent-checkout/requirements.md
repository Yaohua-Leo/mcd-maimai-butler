# 连续选餐、偏好与订单验收规格

用户已确认按四阶段连续实施，完成后统一人工复核；不在阶段之间重复请求方案确认。真实订单创建、取消仍须逐次明确确认，付款由用户在麦当劳官方页面完成。

2026-10-17 用户反馈上一版人工验收无误，授权继续开发真实下单、付款和取消。当前阶段允许为当前验收账号配置限定金额和有效期的真实测试入口；这不代替某笔创建、取消或付款的具体确认。

1. 当用户在结果页提出局部修改时，系统应保留已确认门店、渠道、未修改约束和未指定替换的餐品；本次明确要求覆盖本轮旧要求，旧要求覆盖已授权偏好。每次返回价格、营养、变更说明和可继续编辑的会话版本。失效、过期或并发旧版本不得覆盖新方案。
2. 当用户明确保存偏好时，系统应按当前微信身份持久化预算、口味和排除项；重开恢复。关闭停止使用保存偏好，修改和删除均有入口，删除后会话不得恢复旧记忆。原始聊天、定位、凭据、消费历史不进入偏好存储。
3. 当用户打开确认清单时，系统应从服务端保存的方案生成请求、读取真实餐品详情、调用 calculate-price，显示官方报价、优惠、费用、数量、规格、取餐方式和报价有效期。金额按接口分单位处理。更换方案、取餐方式或报价过期后必须重新确认。报价高于用户预算时不能直接创建订单。
4. 当用户点击最终确认时，只有服务端订单测试/生产开关允许、本次确认凭据匹配方案和金额、且未执行过，才可调用 create-order。重复点击、网络重试和模型文本不得造成重复下单；无明确外部幂等契约时，超时进入待核实，禁止自动重发。
5. 当用户打开官方付款链接或返回小程序时，系统不得据此声明已支付；只有 query-order 的明确状态能更新支付/配餐状态。取消需先选原因、展示后果并明确确认，再调用 cancel-order；结果未知时先查询，不自动重试。
6. 自动测试覆盖上述分支与账号隔离；真实创建、付款、取消的 G2 全链路验收留给用户逐次确认。无明确测试授权的账号默认关闭；已授权账号受单笔金额和有效期限制，不能把代码/模拟测试通过写成 G2 已通过。

首版订单范围延续已实现的到店取餐；不新增外送地址、团餐、自动领券、积分、抽奖或套餐特调编辑。报价使用当前方案的官方默认规格；展示接口已计入的优惠，不自动绑定优惠券。
